# 云端升级说明（待执行）

## 发布顺序

1. 先导出/备份现有数据库与 Storage，并确认 Supabase 项目正确。
2. 在测试项目运行 [002_journal_upgrade.sql](./002_journal_upgrade.sql)。脚本可重复执行，不删除旧回忆、旧图片或日志。若已有同名新表但字段不同，先比较结构，不能假设 CREATE TABLE IF NOT EXISTS 会补齐字段。
3. 确认 memories.photo_urls 是 JSON 数组，格式为 `[{"bucket":"journal-media","path":"用户UUID/文件名.jpg"}]`，deleted_at 可空，photo_url 允许空；保留旧 photo_url 兼容已有图片。
4. 检查策略查询结果，使用两个普通测试账号验证对方的数据和私有文件不可读、不可改；未登录不可访问数据。管理员 SQL 查询不能替代这个验证。
5. 在测试站验证资料、纪念日、计划、多图保存、软删除、恢复、永久删除及照片清理。再安排生产数据库升级，最后发布前端。
6. Supabase Auth Redirect URLs 添加实际生产 `/auth.html` 与需要的 localhost/127.0.0.1 测试地址；恢复邮件流程需真实邮件链接验收。

## 安全变化与限制

- 新照片写入私有 journal-media，路径使用 user UUID，不使用邮箱。显示时生成临时 signed URL。
- memories、资料、计划、纪念日增加 owner-only restrictive RLS；审计日志只能查看/写入本人记录，不能修改或删除。
- 旧 memory-photos 仍是原配置，本次不直接改为私有，避免破坏现有公开链接。旧照片仍可能被持有链接的人访问。
- 完整旧照片隐私迁移需要单独备份、按账号复制到 journal-media、更新 photo_urls、验证显示后再停用旧公开访问；不要先关闭旧 bucket。
- 旧 memory-photos 删除策略必须允许用户删除自己的旧文件。永久删除若返回权限错误，先修正精确到用户目录的策略，不要放开整个 bucket。
- 回收站不会自动清空。永久删除照片和数据库不是原子事务；文件删除成功、行删除失败时会保留记录并可重试，但已经删除的图片无法恢复。
- 本地模拟测试不等同于 SQL 语法、数据库约束、RLS 与 signed URL 的真实集成测试。本环境没有管理连接，未执行此迁移。

## 回退

前端可回退；新增字段和表暂时保留，不要删除已有新数据。旧前端不了解回收站及私有多图，不能把它当作新数据的完整兼容读写端。出现问题时暂停写入并恢复已验证的备份，而不是直接 DROP 表或强行覆盖照片。
